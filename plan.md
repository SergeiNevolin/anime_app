# Техническое задание: Telegram Anime Mini App

## 1. Роль и задача агента

Ты — Senior Full-Stack Engineer и Software Architect.

Необходимо спроектировать и реализовать качественный MVP Telegram Mini App для поиска, каталогизации и просмотра аниме.

Главная задача — создать не просто работающий прототип, а основу продукта с качественной архитектурой, которую можно расширять новыми парсерами, источниками видео, возможностями каталога и пользовательскими функциями без переписывания существующего кода.

Работай самостоятельно: исследуй зависимости, принимай обоснованные технические решения, реализуй функциональность, пиши тесты, проверяй результат и документируй архитектуру.

Не ограничивайся созданием технического плана или демонстрационного интерфейса. Требуется полноценная работающая реализация MVP.

## 3. Основные архитектурные принципы

Придерживаться следующих принципов:

1. Modular Monolith — модульный монолит вместо преждевременного перехода к микросервисам.
2. Clean Architecture — разделять бизнес-логику, инфраструктуру и интерфейсы.
3. SOLID.
4. Dependency Inversion.
5. Explicit interfaces — зависимости между модулями должны быть явными.
6. DRY без чрезмерной абстракции.
7. Fail gracefully — сбой отдельного источника не должен ломать всё приложение.
8. Testability — возможность тестировать бизнес-логику без реальных внешних сервисов.
9. Type safety — использовать строгую типизацию на frontend и backend.
10. Configuration over hardcoding — конфигурация через переменные окружения.

Не создавать сложные абстракции без практической необходимости. MVP должен быть простым в сопровождении, но иметь правильные архитектурные границы.

Все внешние интеграции должны быть изолированы за интерфейсами и адаптерами.

## 4. Функциональные требования MVP

### 4.1. Telegram авторизация

Приложение работает внутри Telegram Mini Apps.

Реализовать:

- Получение `Telegram.WebApp.initData`.
- Передачу исходной строки initData на backend.
- Серверную проверку подписи Telegram.
- Проверку `auth_date` и срока действия данных.
- Защиту от использования поддельных или просроченных данных.
- Создание пользователя при первом запуске.
- Получение текущего пользователя.
- Сопоставление пользователя с Telegram ID.

Основные требования безопасности:

- Никогда не доверять `initDataUnsafe`.
- Не использовать Telegram ID, полученный напрямую с frontend, как подтверждённую идентичность.
- Не хранить Telegram Bot Token в frontend.
- Не сохранять исходный initData в базе данных или логах.
- Использовать постоянную серверную проверку Telegram-идентичности для защищённых API-запросов.
- Сравнивать подписи безопасным способом.
- Ограничить максимальный возраст initData конфигурацией.

В MVP использовать авторизацию через заголовок:

`Authorization: tma <initData>`

Для разработки реализовать отдельный Dev Auth Provider с тестовым пользователем. Он должен работать только при явном разрешении в development-режиме и быть недоступен в production.

### 4.2. Главный экран

Главная страница должна содержать:

- Поиск аниме.
- Недавно просмотренное или продолжение просмотра.
- Раздел популярных или актуальных тайтлов, только если соответствующий источник действительно доступен.
- Быстрый переход в пользовательскую библиотеку.
- Состояния загрузки, ошибки и отсутствия результатов.

Не использовать искусственно сгенерированные данные в production.

### 4.3. Поиск аниме

Реализовать:

- Поиск по названию.
- Debounce запросов.
- Отмену предыдущего запроса при изменении поисковой строки.
- Пагинацию.
- Обработку пустого результата.
- Обработку ошибок внешних парсеров.
- Возможность расширять поиск за счёт новых providers.

Внутренняя модель поиска не должна зависеть от структуры конкретного сайта.

### 4.4. Карточка аниме

На странице аниме отображать:

- Обложку.
- Название на русском, английском и оригинальном языке, если данные доступны.
- Описание.
- Жанры.
- Год выпуска.
- Количество эпизодов.
- Статус выхода.
- Дополнительную информацию, если она предоставляется источником.

Предусмотреть добавление аниме в пользовательскую библиотеку.

### 4.5. Эпизоды и источники

Реализовать:

- Получение списка эпизодов.
- Пагинацию или группировку при большом количестве серий.
- Выбор эпизода.
- Получение доступных вариантов просмотра.
- Выбор источника.
- Выбор качества или озвучки, если они предоставляются источником.

Внутренняя модель должна позволять нескольким providers предоставлять разные варианты воспроизведения одного эпизода.

Не хранить временные подписанные видеоссылки как постоянные данные.

### 4.6. Воспроизведение

Предусмотреть отдельный модуль Player.

Поддержать архитектурно:

- HLS.
- MP4.
- Официальные embed-плееры.
- Открытие официальной страницы источника, если встроенное воспроизведение невозможно.

Использовать hls.js или нативное воспроизведение там, где это поддерживается.

Необходимо обрабатывать:
- Загрузку.
- Ошибки воспроизведения.
- Недоступность источника.
- Переключение источника.
- Выбор эпизода.

Не реализовывать DRM bypass, обход платной подписки, CAPTCHA, геоблокировок, авторизационных ограничений или иных механизмов защиты сторонних сайтов. Использовать только официально доступный или надлежащим образом разрешённый для просмотра контент.

### 4.7. Пользовательская библиотека

Реализовать личную библиотеку аниме.

Статусы:

- PLAN_TO_WATCH.
- WATCHING.
- COMPLETED.
- ON_HOLD.
- DROPPED.

Для каждой записи хранить:

- Пользователя.
- Аниме.
- Статус.
- Текущий просмотренный эпизод.
- Дату добавления.
- Дату последнего изменения.

Функции:

- Добавить в библиотеку.
- Изменить статус.
- Изменить прогресс просмотра.
- Удалить из библиотеки.
- Получить список с фильтрацией по статусу.

Прогресс должен сохраняться между сессиями.

### 5.1. Provider interfaces

Это один из важнейших элементов архитектуры.

Создать независимые интерфейсы:

`AnimeCatalogProvider`

Отвечает за:
- Поиск.
- Получение информации о тайтле.
- Получение эпизодов.

`PlaybackProvider`

Отвечает за:
- Получение вариантов просмотра.
- Получение разрешённых данных воспроизведения.
- Информацию о качестве и озвучке.

`ProviderRegistry`

Отвечает за:
- Регистрацию providers.
- Получение нужного provider.
- Фильтрацию выключенных providers.
- Управление доступностью источников.

`AnicliApiProvider`

Адаптер для интеграции с `anicli-api`.

Он должен преобразовывать объекты и результаты внешней библиотеки во внутренние доменные DTO.

Бизнес-логика приложения не должна импортировать классы `anicli_api` напрямую.

Не привязывать внутреннюю архитектуру к конкретным именам классов, структурам данных и исключениям сторонней библиотеки.

При обновлении `anicli-api` достаточно должно быть изменить интеграционный адаптер и соответствующие тесты.

### 5.2. Поведение providers

Каждый provider должен:

- Иметь уникальный идентификатор.
- Иметь понятное имя.
- Быть конфигурируемым.
- Иметь статусы enabled/disabled.
- Использовать таймауты запросов.
- Нормализовать ошибки.
- Не ломать запросы других providers.
- Поддерживать независимое тестирование.

Использовать allowlist разрешённых источников. Перед включением провайдера проверять условия использования, региональную доступность и права на контент.

Не применять автоматический обход ограничений доступа к сторонним источникам.

### 5.3. Внутренние DTO

Создать независимые Pydantic DTO или доменные модели:

```text
AnimeSummary
AnimeDetails
AnimeGenre
AnimeEpisode
EpisodeSource
PlaybackOption
ProviderInfo
PaginatedResult
```

DTO не должны повторять структуру API AniList, аниме-сайта или `anicli-api`.

## 6. Архитектура базы данных

Использовать PostgreSQL и SQLAlchemy 2.x Async.

Предусмотреть следующие таблицы:

### users

- id — UUID.
- telegram_id — BIGINT, unique.
- username — nullable.
- first_name — nullable.
- language_code — nullable.
- created_at.
- updated_at.
- last_seen_at.

Не собирать избыточные персональные данные.

### anime

- id — UUID.
- canonical_title.
- poster_url.
- created_at.
- updated_at.

### anime_external_refs

- id.
- anime_id.
- provider.
- external_id.
- external_url, если применимо.

Уникальность должна учитывать provider и external_id.

### user_library

- id — UUID.
- user_id.
- anime_id.
- status.
- progress_episode.
- created_at.
- updated_at.

Ограничения:
- Уникальная пара user_id + anime_id.
- Индексы по user_id и status.
- Валидация progress_episode.

Использовать UUID для внутренних идентификаторов.

Добавить необходимые внешние ключи, индексы, unique constraints и check constraints.

Временные playback URL не хранить в постоянной базе.

Все изменения схемы выполнять через Alembic migrations.

## 7. Redis и кэширование

Redis использовать для:

- Кэширования результатов поиска.
- Кэширования информации об аниме.
- Кэширования списков эпизодов.
- Rate limiting.
- Короткоживущих технических данных, если это необходимо.

Для разных типов данных использовать разные TTL.

Не кэшировать видеоссылки дольше срока их фактической валидности. В MVP предпочтительно получать их непосредственно перед воспроизведением.

При недоступности Redis приложение должно корректно работать в деградированном режиме, если это возможно без нарушения безопасности.

## 8. API specification

Все endpoints должны находиться под `/api/v1`.

Предусмотреть следующие маршруты:

```text
GET  /health/live
GET  /health/ready

GET  /api/v1/auth/me

GET  /api/v1/anime/search
GET  /api/v1/anime/{anime_id}
GET  /api/v1/anime/{anime_id}/episodes

GET  /api/v1/episodes/{episode_id}/sources

GET    /api/v1/library
POST   /api/v1/library
PATCH  /api/v1/library/{anime_id}
DELETE /api/v1/library/{anime_id}
```

При необходимости допускается добавление маршрутов, но не следует создавать endpoints без функциональной необходимости.

Требования:
- Типизированные request/response модели.
- Единый подход к ошибкам.
- Валидация входных параметров.
- Пагинация.
- Корректные HTTP status codes.
- Request ID.
- OpenAPI specification.

Формат ошибки должен быть единообразным:

```json
{
  "error": {
    "code": "PROVIDER_UNAVAILABLE",
    "message": "Source is temporarily unavailable",
    "request_id": "..."
  }
}
```

Не возвращать пользователю stack trace или внутренние исключения.

Для frontend генерировать TypeScript-типы из OpenAPI. Не поддерживать вручную две независимые копии одних и тех же API-контрактов.

## 10. UI/UX и дизайн

Цель — минималистичный интерфейс, визуально вдохновлённый классическими приложениями, а не типичным ярким современным стриминговым сервисом.

Основные принципы:

- Спокойная цветовая палитра.
- Чёткая типографика.
- Простые формы.
- Минимум декоративных эффектов.
- Отсутствие тяжёлых градиентов.
- Отсутствие glassmorphism.
- Отсутствие чрезмерно скруглённых карточек.
- Тонкие разделители.
- Понятная визуальная иерархия.
- Хорошая плотность информации.
- Быстрые и понятные взаимодействия.

Придерживаться эстетики классических desktop/mobile приложений: функциональность, аккуратные списки, лаконичные панели и предсказуемая навигация.

Ориентироваться прежде всего на мобильные экраны Telegram Mini App.

### Цвета и темы

- Поддержать светлую и тёмную темы.
- Использовать Telegram theme parameters и CSS variables.
- Не навязывать пользователю цветовую схему, игнорируя настройки Telegram.
- Предусмотреть fallback-тему для обычного браузера.

### Основные UI-элементы

1. Компактная навигация.
2. Поиск.
3. Список результатов.
4. Карточка аниме.
5. Список эпизодов.
6. Выбор источника.
7. Минималистичный видеоплеер.
8. Пользовательская библиотека.

Постеры должны сохранять правильное соотношение сторон.

Предусмотреть:
- Skeleton loading.
- Empty states.
- Error states.
- Disabled states.
- Состояния загрузки действий.
- Touch-friendly элементы управления.

Анимации использовать умеренно. Учитывать `prefers-reduced-motion`.

Не использовать случайные декоративные изображения вместо реальных постеров.

```bash
docker compose up --build
```

Предусмотреть отдельные настройки разработки и production.

Для development обеспечить удобный запуск с hot reload.

Для production использовать оптимизированные сборки Next.js и Python.

Next.js должен использовать production build и Node.js server, а не development server.

Добавить `.env.example`.

## 14. Тестирование — обязательное требование

Тестирование является частью Definition of Done, а не отдельной задачей на будущее.

Нельзя считать MVP готовым, если приложение запускается, но тесты отсутствуют или не проходят.

### 14.1. Backend tests

Использовать pytest, pytest-asyncio, pytest-cov и HTTPX.

Покрыть:

- Telegram initData validation.
- Authentication dependencies.
- Пользовательские операции.
- Anime services.
- Provider registry.
- Интеграцию с anicli-api.
- Playback service.
- Library service.
- API endpoints.
- Database repositories.
- Redis cache.
- Error handling.
- Pagination.

### 14.2. Provider tests

Внешние providers тестировать через mocks и фиксированные fixtures.

Не обращаться к реальным аниме-сайтам во время обычного CI.

Обязательно проверить:

- Успешный поиск.
- Пустой ответ.
- Неверную структуру ответа.
- Timeout.
- HTTP 4xx.
- HTTP 5xx.
- Недоступность отдельного provider.
- Корректное преобразование DTO.
- Отключённый provider.

Добавить contract tests для каждого адаптера.

### 14.3. Frontend tests

Использовать Vitest и React Testing Library.

Покрыть:

- Telegram initialization.
- API client.
- Авторизацию.
- Поиск.
- Карточки аниме.
- Список эпизодов.
- Выбор источника.
- Пользовательскую библиотеку.
- Ошибки и состояния загрузки.
- Навигацию.

### 14.4. E2E tests

Использовать Playwright.

Обязательно проверить сценарии:

1. Открытие приложения с mock Telegram environment.
2. Успешная авторизация.
3. Поиск аниме.
4. Открытие карточки аниме.
5. Просмотр списка эпизодов.
6. Выбор доступного разрешённого источника.
7. Добавление аниме в библиотеку.
8. Изменение статуса просмотра.
9. Изменение прогресса эпизодов.

Для E2E использовать контролируемый тестовый provider, чтобы тесты не зависели от стабильности внешних сайтов.

### 14.5. Coverage requirements

Минимальные пороги:

| Область | Line coverage | Branch coverage |
|---|---:|---:|
| Backend | 85% | 80% |
| Frontend | 80% | 75% |

Для критического модуля Telegram authentication предусмотреть практически полное покрытие всех ветвей проверки подписи и срока действия.

Coverage должен проверяться автоматически в GitHub Actions.

Запрещается исключать из покрытия важную бизнес-логику ради искусственного достижения показателя.

Исключения допустимы для generated code, миграций и внешних адаптеров только при наличии обоснования.

## 15. Безопасность и надёжность

Реализовать:

- Проверку Telegram initData.
- CORS allowlist.
- Rate limiting.
- Ограничения размера входящих запросов.
- Таймауты внешних HTTP-запросов.
- Валидацию входных URL и данных providers.
- Защиту от SSRF и open redirects.
- Безопасную обработку ошибок.
- Сокрытие секретов.
- Исключение токенов и initData из логов.
- Нормализованные логи с request ID.
- Ограничение частоты поисковых запросов.

Не создавать универсальный открытый URL proxy, позволяющий обращаться к произвольным внешним адресам.

Не реализовывать загрузку произвольных видео с внешних сайтов.

Сбой одного provider не должен приводить к 500 для всего поиска, если другие providers могут вернуть результат.

## 16. Производительность

Для MVP не нужна преждевременная оптимизация, но необходимо заложить правильные механизмы:

- Асинхронные внешние запросы.
- Ограничение времени ожидания.
- Параллельное обращение к разрешённым независимым providers.
- Кэширование результатов.
- Пагинация.
- Отмена устаревших запросов поиска.
- Оптимизация изображений.
- Lazy loading постеров.
- Отсутствие загрузки полного списка эпизодов без необходимости.

Не использовать Redis как основную базу данных.

## 21. Требования к качеству реализации

Прежде чем завершить работу:

2. Проверить, что бизнес-логика не смешана с HTTP-обработчиками.
3. Проверить отсутствие циклических импортов.
4. Проверить отсутствие дублирования логики.
5. Проверить, что внешние библиотеки изолированы за адаптерами.
6. Проверить отсутствие временных mock-данных в production.
7. Проверить корректность всех миграций.
8. Проверить security-sensitive участки.
9. Проверить Docker images.
10. Проверить все CI jobs.

Если интеграция с конкретным источником объективно невозможна из-за его недоступности, не подменять её фиктивной реализацией. Зафиксировать ограничение и обеспечить корректное поведение всей системы.
